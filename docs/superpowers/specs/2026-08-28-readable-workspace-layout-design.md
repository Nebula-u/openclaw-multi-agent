# 可读工作区目录布局设计

## 目标

后续创建的工作流任务不再把工作副本、输入、产物和日志深置于 `runtime/`，并且不再以长工作流、任务或执行 ID 作为目录名。新布局应让维护者可以直接从项目根目录识别任务用途，同时不降低现有身份校验、隔离和审计能力。

本次不迁移、不重命名，也不删除已有的 `runtime/artifacts/` 和 `runtime/worktrees/` 内容。

## 范围

### 包含

- 后续任务的工作副本、输入、输出和日志迁移到项目根目录的 `work/`。
- 为任务目录生成稳定、简短、可读的名称。
- 让 Orchestrator、沙箱准备、结果收集和测试使用新路径。
- 调整安装脚本创建的目录和相关文档。
- 为命名、冲突、路径约束和新任务完整流程补充自动化测试。

### 不包含

- 迁移、清理或重写已有 runtime 数据。
- 改变 SQLite 中的 `workflow_id`、`task_id`、`run_id` 或 `execution_id` 格式。
- 改变 Agent 的权限、沙箱边界、JSON 契约或快照语义。

## 目录布局

每个后续任务使用如下目录：

```text
work/
  <项目名>-<任务摘要>/
    repo/
    input/
      task.json
      context.md
      context-manifest.json
      user-request.md
    output/
      result.json
    logs/
      agent-output.jsonl
```

示例：`work/storefront-add-login/`。

`runtime/` 继续只承担控制数据库、已安装 Agent、运行时 bundle 和短期控制命令队列的职责。新任务不在 `runtime/` 下创建 worktree、任务输入、结果产物或执行日志。

## 命名规则

- 项目名取目标项目根目录的 basename，转换为小写连字符形式。
- 任务摘要取任务标题，转换为小写连字符形式；移除路径分隔符与其他不安全字符，合并重复连字符，并截断到可读的固定上限。
- 项目名或任务摘要清理后为空时，分别使用 `project` 和 `untitled-task`。
- 完整目录名形如 `<project>-<summary>`，发生冲突时顺序追加 `-2`、`-3` 等短序号。
- 不将 `workflow_id`、`task_id`、`run_id` 或 `execution_id` 放入目录名；这些完整值仍保留在 JSON 元数据和 SQLite 中，作为唯一身份和关联依据。

## 数据流与兼容性

Orchestrator 在创建任务时分配 `work/<可读目录>/`，并将该目录下的绝对路径写回任务记录。后续模块继续通过记录中的绝对路径工作，因此任务消息、结果校验、沙箱 staging、快照和审计不会依赖目录名来判断身份。

工作副本位于 `repo/`，不可变任务输入位于 `input/`，发布后的结果位于 `output/`，原始 Agent 输出和命令日志位于 `logs/`。重试或失败恢复会创建一个新的可读目录，绝不覆盖既有任务目录；各次关联由 SQLite 中的 ID 保证。

历史任务维持旧路径。读取历史任务时，系统继续使用数据库中已有的绝对路径，不触发迁移或回填。

## 安全与错误处理

- 所有新目录都必须在 canonicalize 后确认位于项目根目录的 `work/` 内，拒绝路径穿越、链接逃逸和不安全标题字符。
- 目录占用时，仅在安全地找到未占用的递增序号后创建；无法创建时明确失败，不回退到 `runtime/`。
- 标题缺失、为空或仅含被清理字符时采用明确的可读默认名。
- 运行时控制目录仍在 `runtime/`，不与 `work/` 混用。

## 验证

- 单元测试覆盖：标题规范化、默认名、截断、序号冲突与路径越界拒绝。
- Orchestrator 流程测试覆盖：新任务路径位于 `work/`、固定子目录和文件存在、Agent 输入输出路径正确。
- 沙箱与结果收集测试确认它们使用任务记录提供的新绝对路径，且不暴露额外宿主目录。
- 安装与运行时 bundle 测试确认安装不再为新任务创建 `runtime/worktrees` 和 `runtime/artifacts`，并仍能正常安装、校验与启动。
- README 明确新目录布局、旧数据不迁移和已安装 Agent 更新命令。
